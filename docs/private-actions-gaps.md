# Private Actions V1 — open gaps

What is *not* finished, kept here so that no part of it can be quietly
mistaken for done. Ordered by dependency, not by size.

Companion to [private-actions-architecture.md](./private-actions-architecture.md)
and [private-actions-privacy-model.md](./private-actions-privacy-model.md).

## Closed

### Server-side EIP-712 verification — closed

`POST /v1/intents` and `POST /v1/intents/{id}/authorization` verify the
submitted signature against the claimed signer, in `crates/bte-coordinator/src/eip712.rs`.

Until this landed, both endpoints checked only that the signature was *hex*.
`pseudonymousSigner` was therefore an unauthenticated string, and anyone could:

- submit intents attributed to any address, poisoning the replay index, the
  ordering commitment and the receipt; and
- authorize *somebody else's* intent — worse, because that endpoint takes a
  client-supplied digest, so a stranger who learned an intent id could bind it
  to a quote of their choosing.

The digest is rebuilt server-side from the fields being stored, never taken
from the request. The Rust digest is pinned against a vector generated by viem
so the two implementations cannot drift apart silently.

## Open

### 1. Authorization → quote binding

`post_authorization` proves the intent's owner signed *this hash*. It does not
yet prove the hash covers the quote the agent was actually shown.

The fix is to send the `ExecutionAuthorization` fields rather than a
precomputed digest, and rebuild the digest server-side the way the intent path
already does. `AUTHORIZATION_TYPES` in `packages/actions/src/sign.ts` already
defines the struct: `quoteHash` and `callHash` are what make it specific.

### 2. Reveal → intent binding

A revealed plaintext is not yet provably the same intent that was ordered. The
`orderingRoot` commits to `intentId || ciphertextHash` before any share exists;
the reveal path does not yet check a plaintext back against that leaf.

### 3. Inclusion proofs

`GET /v1/batches/{id}/commitment` returns the root. There is no endpoint that
returns a Merkle path, so a client can be told a root but cannot verify its own
intent is under it. Needs the sibling path served alongside the position.

### 4. Share evidence exposure

The partial decryption shares that justify a reveal are held but not served, so
a receipt's crypto claims currently rest on the coordinator's word.

### 5. Receipt assembly

No `GET /v1/intents/{id}/receipt`. The pieces exist — lifecycle events,
commitment timestamp, ordering root — but nothing assembles and returns them.

### 6. Commitment signing

`batch_commitments.signature` is written `NULL`. An unsigned commitment is
still ordering evidence but it is not attributable, so a coordinator could
equivocate between clients and nothing would prove it.

**This may be deleted rather than built.** See below.

### 7. Executor service and example agent

Adapters exist and are shape-verified; `execute()` deliberately throws
`NOT_IMPLEMENTED` so an adapter can never broadcast. Nothing drives the
authorized → submitted → settled tail, and there is no worked agent example.

## The decision that sits above items 4 and 6

EIP-2537 is live on Base mainnet and Base Sepolia — verified by calling the
precompiles directly, not inferred:

| chain | `0x0b` G1ADD | `0x0f` pairing check |
|---|---|---|
| Base Sepolia | returns 128 zero bytes | returns `1` |
| Base mainnet | returns 128 zero bytes | returns `1` |
| Ethereum mainnet | returns 128 zero bytes | — |

Control: address `0x…ff` with identical input returns `0x`, so the probe
distinguishes a real precompile from an empty account.

So BLS12-381 pairings are reachable from Solidity on the target chain. If
`e(pd_j, g_2) == Σ_i e(ct_{i,0}, v_j^i)` verifies within a sane gas budget for
a realistic batch, a valid share *becomes* the attestation: item 6 disappears
entirely, and item 4 becomes onchain rather than an API concern.

Benchmark that before building either. The term count scales with batch size
(~`1 + B` pairings per share), so the answer may be "fits at B=16, not at
B=64", which is tuning rather than redesign.

Caveat that survives a good result: verifying a share is not decrypting one.
Recovering plaintexts still needs FFT plus FO decryption, which is not going
onchain. Onchain verification removes the trust assumption about *who
attests*, not the committee itself.

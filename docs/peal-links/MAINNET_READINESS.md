# Peal Links mainnet readiness

Mainnet is an explicit release state, not a configuration flag. This file lists every requirement that stands between the local demo and real money, with its current status. Nothing below is claimed as done unless a command, a file, or a third party's document is cited. Last updated 2026-09-16 (Phase D).

## Status summary

| Area | Status | What exists | What is missing |
|---|---|---|---|
| Cryptographic soundness of the payment protocol | **blocked** | Knowledge soundness and zero knowledge of ZK-Pari are proven in the paper (Theorems 4, 5) | Simulation extractability, which the payment protocol relies on, is deferred by the paper (Remark 2). No later proof found on 2026-09-16 |
| Trusted setup | **blocked** | `Keys::generate` runs the per-circuit setup in one process and discards the trapdoor | A multi-party ceremony for R_op and R_dep at the pinned revision, with published transcripts and the resulting circuit id pinned in configuration |
| Upstream code maturity | **blocked** | zk-pari PR #2 head `a8266aac`, 31 upstream tests pass, pinned by revision | The PR is open and unreviewed; the paper calls it a prototype. No external security review of the circuits or of Peal's integration |
| Poseidon parameters | **blocked** | Generated by the reference Grain LFSR in upstream `hasher.rs` | The reference implementation's matrix security checks, which upstream says a deployment must run |
| Ledger decentralisation | **blocked** | Single-node ledger actor with deterministic ordering, batched verification, chained state root, full replay | Commonware `simplex` integration with three or more validators; validator key management; state sync |
| Settlement trust | **committee-trusted by design** | `PealLinksGateway`: threshold ECDSA certificates over EIP-712, epochs, unique ids, caps, pause, reentrancy guard; 9 Foundry tests plus a Rust/Solidity digest cross-check | Independent signer operators with separate key custody (the local fixture holds all keys in the node); a timelock and multisig on the gateway owner; monitoring; a proof-verified settlement path (see below) |
| Deposits | **local only** | Watcher credits `Deposit` events after `confirmations`, deduplicated by `chain:tx:logIndex`, block-hash reorg detection, intent-first credit path proven by R_dep | Chain-specific finality policies for Ethereum (safe/finalized tags), Base and Arbitrum (L2 sequencer and L1 settlement assumptions); a verified deployment on each; a verified token allowlist with on-chain code checks |
| Configuration | **profiles only** | `config/` carries local profiles; `NamespaceConfig` validates shapes and refuses `enabled` without gateway, token and RPC | Mainnet profiles with gateway addresses, token addresses verified against official sources, explorer URLs, and `enabled: true` only after the watcher's chain check |
| Keys and secrets | **local fixture** | Signer keys read from a file the stack script writes; refused with a mainnet namespace | HSM or KMS-backed signers, key rotation runbook, no keys on disk |
| Product security | **partial** | EIP-4361 sessions, signed manifests, account-signed inbox reads, rate limits by body size, problem+json errors | Per-IP and per-account rate limits, CSP on the explorer, abuse controls on the public-write inbox, session revocation, audit logging without identifiers |
| Availability and recovery | **partial** | sqlite WAL stores, replayable ledger, encrypted client backups with anti-rollback conflict detection | Replicated storage, archive of receipt paths beyond the wallet's pruning horizon, operator runbooks for restore, disaster recovery drills |
| Testing on public testnets | **not started** | Adapters and scripts are chain-agnostic | A run against Sepolia, Base Sepolia and Arbitrum Sepolia with test assets, recorded in BUILD_STATUS.md |
| External review | **none** | | Review of the circuits' integration, the ledger STF, the gateway, the node API |

## Activation checklist (all required)

1. A deployed gateway per namespace with its address, code hash, deployment block and owner recorded in the mainnet profile, and the owner behind a timelock and multisig.
2. A token allowlist per namespace where every token address and decimals value was verified against the issuer's official documentation and the on-chain code, with fee-on-transfer and rebasing tokens excluded.
3. Settlement signers run by independent operators, each verifying the ledger record before signing, with keys in HSMs and a rotation procedure exercised at least once.
4. A finalized-ledger health check: the node refuses to sign withdrawals unless its ledger replays cleanly and the watcher's cursor is within a bounded lag of each chain head.
5. Proving keys from a ceremony, with the circuit id pinned in configuration and the node refusing to start under a different id in the `production` profile.
6. The simulation-extractability question resolved, or an explicit written risk acceptance by the operator that the payment protocol's security argument is incomplete.
7. Documented security review of the items above, with findings addressed.

## The upgrade path from committee attestation to proof-verified settlement

Not implemented. A proof-verified adapter would have the gateway verify a succinct proof that the ledger's state transition burned `amount` for `withdrawalId`, which needs: a recursive or aggregate proof over the ledger's batch of R_op proofs plus the burn opening; on-chain BLS12-381 pairing verification (EIP-2537 on Ethereum mainnet; availability on Base and Arbitrum must be checked per chain); and data availability for the receipt log so a user can exit without the operator. Until then the bridge is committee-attested and described as such everywhere it appears.

## What a user can and cannot do if the operator disappears

- Funds inside the private ledger cannot be withdrawn without a live ledger and a signer threshold. This is a custody risk equivalent to the committee, stated in the product copy.
- A user with their encrypted backup keeps their account opening and receipt openings, and could prove ownership to a successor operator running the same circuit id and ledger history, but nothing in this build automates that.

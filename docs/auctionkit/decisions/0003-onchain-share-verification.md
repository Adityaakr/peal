# 0003 — Onchain share verification is affordable on Base

**Status:** accepted · **Date:** 2026-08-26 · **Supersedes the open question in [0001](./0001-reveal-root.md)**

## Context

[0001](./0001-reveal-root.md) chose a committee-attested reveal root over
onchain share verification, and closed by saying the decision should be
revisited "soon, and with a benchmark rather than an argument."

This is that benchmark.

## EIP-2537 is live on Base

Verified by calling the precompiles directly over JSON-RPC, not inferred from
release notes:

| chain | `0x0b` G1ADD | `0x0f` PAIRING_CHECK |
|---|---|---|
| Base Sepolia | 128 zero bytes | `1` |
| Base mainnet | 128 zero bytes | `1` |
| Ethereum mainnet | 128 zero bytes | — |

Control: address `0x…ff` with identical input returns `0x`, so the probe
distinguishes a live precompile from an empty account. This RPC probe — not the
forge test below — is the evidence that Base has it, because foundry's local EVM
implements EIP-2537 too and would give the same numbers on a chain that did not.

## Measured cost

`contracts/test/auctionkit/BlsPairing.t.sol`, against a Base fork.

Peal's share check is `e(pd_j, g_2) == Π_i e(ct_{i,0}, v_j^i)`, which rearranges
to `e(pd_j, -g_2) · Π_i e(ct_{i,0}, v_j^i) == 1` — a single product the
precompile accepts, costing `1 + B` terms per share.

Marginal cost is **32,699 gas per term**, linear across k = 1…65, matching the
EIP-2537 formula `32600k + 37700`.

| B | terms | gas / share | gas / reveal (t=3) |
|---:|---:|---:|---:|
| 4 | 5 | 201,918 | 605,754 |
| 8 | 9 | 332,623 | 997,869 |
| 16 | 17 | 594,060 | 1,782,180 |
| 32 | 33 | 1,117,043 | 3,351,129 |
| **64** | **65** | **2,163,439** | **6,490,317** |

At B=64, t=3 — 74,880 bytes of calldata per reveal:

| component | wei |
|---|---:|
| L1 data fee (`GasPriceOracle.getL1Fee`) | 400,518,599,276 |
| L2 execution @ 0.006 gwei | 38,941,902,000,000 |
| **total** | **39,342,420,599,276** (≈ 0.0000393 ETH) |

The L1 data fee is **1% of the total** — the intuition that data availability
dominates on an L2 is wrong here, and was worth measuring rather than assuming.

Base mainnet's block gas limit is 400,000,000, so a full reveal is ~1.6% of a
block.

## Decision

**Onchain share verification is affordable at the batch size AuctionKit already
uses.** B=64 needs no tuning; the sweep is retained so a future change to B has
a number attached rather than a guess.

Consequently the committee *signature* layer in `SealedBidAuction` can be
replaced by onchain verification: a valid share *is* an attestation, so
`CommitteeRegistry`'s signing addresses, key rotation, and the equivocation risk
of a committee that signs two different roots all disappear.

This is not yet implemented. It is now a scheduled replacement rather than an
open question, and [0001](./0001-reveal-root.md) stands until it lands.

## What this does not do

**Verifying a share is not decrypting one.** Recovering plaintexts still needs
an FFT and FO decryption, neither of which is going onchain. This removes the
trust assumption about *who attests* that a share is valid. The committee still
holds the key material and can still refuse to decrypt — that is a liveness
failure with the existing permissionless `failOnRevealTimeout()` recovery path,
and it is unchanged.

**The per-bid commitment check stays either way.** It is what binds a plaintext
to a bidder, which share verification does not address.

## Known gaps in this measurement

1. **Placeholder points for the gas curve.** The precompile charges by term
   count regardless of point values, so the gas figures are exact. Correctness
   of the encoding is proved separately by `test_realPairingRelationHolds`
   (`e(P,Q)·e(-P,Q) == 1` over real generators, vectors generated by
   `cargo run -p bte-crypto --example eip2537_vectors`) and its negative control
   `test_realPairingRelationFails`.
2. **The verification key shares `v_j^i` are not yet onchain.** Getting them
   there — storage versus calldata, and who pays — is unmeasured and is the next
   thing to size.
3. **0.006 gwei is a snapshot.** Base gas can spike; the gas *counts* are stable,
   the fiat cost is not.
